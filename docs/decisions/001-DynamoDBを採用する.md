# 001 — DynamoDBを採用する

データベースはAmazon DynamoDBの1テーブルとする。PostgreSQLや外部のマネージドDBは使わない。

## 理由

- VPCが要らず、Lambdaからそのまま使える。
- 期限なしの無料枠（25GB、読み書き各25ユニット）に収まる。
- CDKでは1つのconstructで済み、構成管理が最小になる。

## 経緯

当初はPostgreSQLの全文検索と `pg_trgm` のあいまい一致で候補を絞る設計だった。その後、絞り込みを自前の文字3-gramで行う方針に変わり（[search.md](../search.md)）、データベース側の検索機能が不要になった。検索機能が要らなければ、リレーショナルDBを選ぶ理由も薄れる。

なお、DynamoDBを選んでも [004](004-Amplify-Dataを使わない.md) を覆すことにはならない。Amplify Dataは「AppSync（GraphQL）+ スキーマから自動生成されるDynamoDB」のセットであり、本判断ではDynamoDBのテーブルと権限を自前のCDKで定義し、APIはRESTのまま保つ。共通するのはDynamoDBという部品だけである。

## 検討した代替案

| 案 | 無料枠 | 不採用の理由 |
|---|---|---|
| Aurora Serverless v2 | なし | 待機中もストレージ課金（$0.10/GB・月）。稼働時は1 ACU時あたり $0.12（米国）〜$0.20（東京）。停止からの再開に十数秒かかる。Lambdaから使うにはVPC構成かData APIの有効化が要る |
| Neon | あり（0.5GB、月100CU時間、5分無操作で自動停止、転送5GB） | AWSの外にアカウントと接続文字列が増える |
| Cloudflare D1 | あり | 正規の利用経路がWorkersのバインディングに限られる。LambdaからはRESTの `/query` 経由になり、Cloudflare API全体の上限（1,200リクエスト/5分・利用者単位）を共有する |

## トレードオフ

- 全件読み出しがScanになる（数万件で遅くなる）。
- 複数条件の絞り込みをデータベース側で組めない。絞り込みはアプリケーション側の実装になる。
