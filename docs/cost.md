# 費用が暴走しない仕組み

無料枠に収まる構成を基本にしつつ、botに叩かれても請求額が有界になるようにする仕組みを説明します。金額は2026-08時点の単価による計算で、実測ではありません。

## なぜ仕組みが要るか

従量課金のサーバーレス構成で最悪なのは「落ちる」ことではなく「請求」です。AWSには支出の強制的な上限が原則としてありません。AWS Budgetsは課金データの反映が数時間から半日遅れるため、突発的な増加を止める用途には使えません。だから、事前の設定でレートに蓋をして最悪額を固定します。

## 支配的なのはLLM費用

API GatewayとLambdaの単価は低く、叩かれ続けても月数ドルで済みます。支配項はLLM（Luna）の呼び出しです。単価は100万トークンあたり入力 $0.22 / 出力 $1.32 で、1検索を入力800・出力200トークンとすると1回約 $0.00044 です。

| 制限 | 1日の回数 | 日額 | 月額（30日） |
|---|---|---|---|
| 制限なし（毎秒1回で張り付かれた場合） | 86,400 | $38 | $1,140 |
| 毎秒0.1回に制限 | 8,640 | $3.80 | $114 |
| 日次カウンタ300回 | 300 | $0.132 | $3.96 |
| 通常の利用（1日100回） | 100 | $0.044 | $1.32 |

制限なしと毎秒0.1回の差は10倍。この差が、AIを呼ぶ経路だけを強く絞る理由です（判断の記録は [decisions/003](decisions/003-AIを呼ぶ経路を毎秒0.1回に絞る.md)）。

## 入れる仕組み（CDKで定義する）

- **AIを呼ぶ経路のスロットリング** — AIを呼ぶ経路（初版は `POST /search`）はAPI Gateway上に明示的なルートとして定義し（他は `/{proxy+}` でHonoへ委ねる）、ルート別設定で毎秒0.1回・バースト2に絞る。これが硬い上限で、張り付かれても月約 $114 で止まる。毎秒1回未満の値が実際に効くかは未検証（[decisions/003](decisions/003-AIを呼ぶ経路を毎秒0.1回に絞る.md)）。
- **LLMの日次カウンタ** — DynamoDBの `pk = COUNTER#llm` / `sk = <日付>` を条件付きの原子加算で数え、1日300回程度を超えたらAI経路を429で止める。コールドスタートをまたいで数えられる。普段の利用を守る柔らかい上限。
- **Lambdaの同時実行数の固定** — 2〜5に固定する。0にすれば全停止できる操作点になる。
- **API全体のスロットリング** — 既定ルートにも小さめの上限を掛ける。
- **robots.txtで巡回を断る** — PoCは検索エンジンに巡回される必要がない。無差別クローラーの無駄な呼び出しを最も安く止める。
- **CloudWatch Logsの保持期間7日** — ログの保存費用を抑える（無料枠は取り込み5GB/月）。

CloudWatchアラームは任意です。入れる場合はBedrockの `Invocations` を日次合計で監視します（アラーム10本・メール1,000通/月まで無料）。自動停止まで要るなら、SNSからLambdaを呼んで同時実行数を0にします。AWS Budgetsは $5 と $20 の2段を目安に置きますが、反映が遅いため検知用であり防御にはなりません。CloudflareとAWS WAFは使いません（理由は [decisions/002](decisions/002-Cloudflareを使わない.md)）。

補足：ログインやCAPTCHAは「壁」ではなく、攻撃者に単価を課す層です。CAPTCHAの代行は1,000回 $1〜3 程度で突破されます。ただし無差別に巡回するプログラムはその費用を払わないため、課金事故の主犯である層はそこで落ちます。検索は公開機能なので利用者単位の上限は掛けられず、上のレート制限が本命になります。

## LLM以外の費用

- DynamoDBはプロビジョンドモードの期限なし無料枠（25GB、読み書き各25ユニット）に収まる。
- LambdaとAPI GatewayはPoCの利用量なら無料枠内。
- Amplify Hostingの無料枠は12ヶ月型。期限後の費用が合わなければ、素のS3 + CloudFront配信へ戻せる依存度に留める。
